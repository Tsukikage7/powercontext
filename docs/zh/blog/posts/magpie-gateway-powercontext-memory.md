最近我给 [Magpie](https://github.com/yetone/magpie) 社区插件仓库贡献了一个 PowerContext 插件，包名是 `@magpie-community/gateway-powercontext`，目前版本 0.2.1，已经可以在 Magpie 的插件发现页里直接安装。这篇文章整理一下它的设计思路、实现细节和一路踩过的坑。

文章比较长，前半部分讲为什么要做、怎么用，后半部分讲实现。只想上手的话，看完第三节就够了。

## 一、问题从哪里来

我日常会同时用好几个编程 Agent：Claude Code、Codex，偶尔还有 Gemini CLI。用得久了，一个很具体的麻烦是项目约定没法跨工具保留。比如某个仓库部署统一用 Helm，跑测试要先设置一个临时 HOME，某个目录下的生成文件不要手改。这些东西在一个会话里讲清楚了，换一个客户端，或者第二天开一个新会话，就得重新交代一遍。

长期记忆服务已经有不少了，PowerContext 是其中做得比较完整的一个。它是 OceanBase 开源的 Agent 记忆服务，除了基础的 Memory，还有用户画像（Profile）、跨会话交接（Handoff）、按主题组织的 Topic Memory，以及从任务结果里沉淀经验的 Experience。

问题在于接入方式。常见的做法是给每个客户端单独配：装一个 MCP Server，写一份 Skill 或者在系统提示里加一段说明，让模型在合适的时候主动调用记忆工具。这样做有几个现实的缺点：

第一，每个客户端都要配一遍，配置分散在各处，换机器或者新增客户端都得重来。

第二，是否查记忆取决于模型自己的判断。模型忘了调用、调用时机不对、查询词写得不好，召回效果都会打折扣。

第三，MCP 工具调用本身会占用一轮推理，会话里也会多出一段工具调用记录。

我用 Magpie 已经有一段时间了。它是一个本地模型网关，可以让 Claude Code 跑 Kimi、让 Codex 跑 DeepSeek，在菜单栏里切换模型和账号。既然所有客户端的请求本来就都要经过 Magpie，那么在网关这一层统一做记忆召回和对话存档，客户端就完全不用感知记忆的存在了。这就是这个插件的出发点。

## 二、它做了什么

插件在一次请求的生命周期里做两件事。

**推理前召回。** 请求进入 Magpie、还没发往模型之前，插件取出这次请求里最新一轮用户输入，去 PowerContext 查询相关的 Memory 和 Profile。如果这是会话的第一轮，还会同时取一份最近的 Handoff 提示，方便新会话接上之前的工作。查到的内容会被包装成一段带标签的参考文本，附加到最新一条用户消息的末尾，然后 Magpie 照常把请求发给模型。

**回复后存回。** 这一项默认关闭，需要用户主动打开。模型回复结束后，Magpie 会通知插件，插件把这次的完整对话异步写回 PowerContext，作为一条内容来源（Source）。这里的完整对话包括用户消息、助手回复，以及客户端自己执行的工具调用和结果。PowerContext 会按照服务端配置的调度，在后台用生成模型把这些来源提炼成新的 Memory 和 Topic Memory。

这两步加起来形成一个闭环：今天在 Codex 里的对话被存回、提炼，明天在 Claude Code 里提问时就能被召回。

对客户端而言，它只是把模型地址指向了 Magpie，不需要安装 MCP，不需要 Skill，也不需要在提示词里提醒模型去查记忆。

插件支持 Magpie 网关目前接入的四种协议：OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 和 Gemini。请求以什么协议进来，就以什么协议出去，插件只在对应协议的用户消息结构里追加文本，不做协议转换。

## 三、怎么用

**部署 PowerContext。** 插件本身不负责安装或启动 PowerContext，需要先按 PowerContext 文档的[快速开始](https://powercontext.oceanbase.io/zh/docs/get-started/quickstart/)独立部署一个 Server。如果希望存回的对话能自动提炼成记忆，需要在 Server 端配置生成模型和记忆调度；希望语义检索效果好一些，还要配置 Embedding 模型。这部分配置和插件无关，属于 PowerContext 服务本身。

**安装插件。** 需要 Magpie 0.1.1273 或更新的版本。可以在 Magpie 的插件页面里打开“发现”，搜索 PowerContext 直接安装，也可以用命令行：

```sh
magpie plugin add @magpie-community/gateway-powercontext
magpie plugin options @magpie-community/gateway-powercontext '{"serverUrl":"http://127.0.0.1:8000"}'
```

**填写连接信息。** 插件带了一个配置页，可以填写 Server 地址、可选的 Scope ID 和服务密钥，并控制是否开启对话存回。密钥直接填 token 即可，页面会自动加上 `Bearer` 前缀。Scope ID 可以留空，留空时会按会话和工作区的绑定关系，或者 Server 的默认 Scope 来解析。

这里有一个版本上的细节：Magpie 0.1.1531 修复了一个问题，之前带 hook 的插件会被当成纯页面插件，导致在配置页保存的设置要重启 Magpie 才能生效。建议直接用 0.1.1531 以上的版本。

配置完成后，客户端照常通过 Magpie 发请求即可。可以在 PowerContext 的管理面板里看到存回的来源和提炼出的记忆，在 Magpie 的插件诊断里看到每次 hook 的执行结果，比如召回成功、无结果、跳过或者服务不可用。

## 四、先给 Magpie 补上异步 hook

做这个插件时，第一个障碍其实在 Magpie 本身。

Magpie 原有的网关中间件是同步执行的，运行在一个嵌入式的 JS 引擎里，适合做请求改写这类纯计算的工作，但没法在推理之前发起一次网络请求并等待结果。记忆召回恰恰需要这一步：先去记忆服务查，查到了再发给模型。

所以我先在 Magpie 仓库提了一个 issue（[yetone/magpie#2118](https://github.com/yetone/magpie/issues/2118)），提议增加两个可选的能力：

一是推理前可以等待的异步 hook。它有明确的截止时间，跟随客户端请求一起取消，失败时保留原始请求。

二是回复结束后的完成通知。它是尽力而为的，不会阻塞客户端的流式输出。

讨论中和维护者达成的一个关键共识是：网关对每个客户端请求只发起一次模型推理。hook 只能往请求里补充上下文，不能注册工具，也不能自己驱动多轮推理循环。工具的执行和后续推理仍然由客户端负责。这条边界很重要，它保证 Magpie 依然只是网关，不会因为接入记忆而变成另一个 Agent 运行时。

我在自己的 fork 里实现了这套机制，维护者 review 之后把它移植进了主线，随 Magpie v0.1.1273 发布，入口命名为 `magpie.hooks`。移植时维护者做了一处调整：我最初用的入口名 `magpie.gateway` 已经是同步中间件的别名，一个导入了 `node:fs` 的 hook 文件会被同时当作中间件加载，然后在嵌入式引擎里报错。正式版本把 hook 和中间件的命名彻底分开了。

现在的 hook 协议大致是这样：插件在 `package.json` 里声明 `magpie.hooks` 入口，导出 `async onRequest(body, ctx)` 和可选的 `onResponse(reply, ctx)`，两者运行在 Bun 插件宿主里，可以正常使用 Node 生态的 API 发起网络请求。`ctx` 里带有协议类型、模型、是否流式、会话、工作目录、请求来源分类、插件配置、一个 `AbortSignal`，以及上报诊断信息的接口。客户端的请求头和凭证不会传给 hook。

宿主对 hook 有几条硬性约束，我觉得设计得很克制：

- hook 抛异常、超时、返回非法数据时，对请求的修改全部回滚，原样发给模型。
- 如果 hook 改动了客户端声明的工具、tool choice、`model` 或 `stream` 字段，同样回滚。这些字段关系到鉴权和客户端对响应格式的预期，插件不应该碰。
- 被回滚的 hook 在这次请求里不会收到 `onResponse`。
- 整条 hook 链有十秒的总时限，单个插件可配置的时限是 100 到 10000 毫秒。

这套 hook 不是只给记忆用的。任何需要在推理前等待外部 I/O 的插件，比如查询知识库、做内容审计、挂接内部上下文服务，都可以基于它来写。

## 五、召回链路的实现细节

插件的核心代码在 `powercontext.hooks.mjs`，六百多行，没有任何依赖，再加上一个负责解析各协议对话格式的 `conversation.mjs`。下面按一次请求的顺序讲几个值得说的点。

### 先判断要不要做

插件在发出任何请求之前要先过几道检查。没有配置 `serverUrl` 时直接跳过，插件没有默认地址，所以不配置就不会有任何外部请求。

然后看请求来源。Magpie 宿主会给每个请求标一个来源分类：直接从本机回环地址发来、没有转发头、也没有使用命名网关密钥的请求是 `local`；其他情况分别是 `magpie-key`、`gateway-key` 或 `remote`。这个分类由宿主根据连接信息判断，客户端无法伪造。插件默认只对 `local` 请求做召回和存回。

之所以这样设计，是因为 Magpie 支持局域网共享，也可以给别人发网关密钥。如果对所有请求都做召回，别人通过你的网关发起的请求就能读到你的记忆，他的对话也会被存进你的记忆库。所以对非本机来源的召回和存回分别需要显式开启，对应两个独立的选项 `recallRemote` 和 `captureRemote`。开启存回的权限并不意味着能读取记忆，这两者在代码里是分开判断的。这一点是在 review 中被维护者指出来之后修正的，后面会再提到。

最后看服务是否处于退避期。如果同一组 Server 地址、凭证和 Scope 最近连接失败、超时或者返回服务不可用，插件会在退避期内（默认 30 秒）直接跳过，不查询服务，也不回放缓存。这样当 PowerContext 挂掉时，每个请求不会都白白等一次超时。

### 解析 Scope

PowerContext 用 Scope 来隔离不同项目或不同用户的记忆。插件调用 `v1/scope-bindings/resolve`，把 Magpie 提供的会话 ID 和工作目录作为绑定键发过去，由服务端决定这次请求属于哪个 Scope。如果用户在配置里指定了 Scope ID，会作为显式值一并发送。

工作目录在发送前会先规范化，再做 SHA-256 摘要，服务端拿不到原始路径。找不到绑定时插件不会主动创建 Scope，而是放弃这次召回，请求照常进行。插件也不会给模型任何修改 Scope 的能力，注入的参考文本里会明确说明 Scope ID 只用于标识召回来源，不代表可以变更 Scope。

### 并行取上下文和 Handoff

Scope 确定后，插件调用 `v1/context/prepare` 取召回内容，查询词是最新一轮用户输入，返回内容受 `maxBytes` 限制，默认 8000 字节。如果这是会话里的第一条用户消息，还会同时调用 `v1/handoff/hint` 取最近一次提交的 Handoff。两个请求用 `Promise.all` 并行发出，各自有独立的超时（默认 1000 毫秒，包括读取响应体的时间）。

查询词的选取有一个细节。Codex 这类客户端会在用户消息里夹带环境信息、指令文件内容和各种系统提示，直接用整条消息做查询会稀释召回效果。Magpie 宿主在 `ctx.query` 里提供了一个只包含用户实际输入的版本，插件优先用它做查询，同时保证发给模型的原始消息不被改动。

Handoff 是可选的。没有已提交的 Handoff 时服务端会返回 404 或 503，这是正常情况，不会触发退避。Handoff 接口本身连接失败或超时，只会对 Handoff 这一个接口单独退避，不影响正常的记忆召回。

还有一个兼容处理：插件会优先请求按段落组织的 Markdown 格式结果。如果服务端版本较旧、不支持这个参数而返回 422，插件会在接下来十分钟内退回到不带格式参数的请求。

### 注入参考文本

取回的内容会被包进一对 `<powercontext-reference>` 标签里，前面附一段说明，告诉模型这是参考资料，不是用户指令。然后追加到最新一条用户消息的末尾。

这里需要考虑提示注入。记忆内容本质上来自过去的对话，可能包含任何文本，包括一段伪造的闭合标签。插件会把召回内容里出现的 `<powercontext-reference` 和 `</powercontext-reference` 转义掉，保证召回的文本无法提前闭合它所在的块，伪装成块外的内容。

### 保持 prompt cache 命中

这是实现里花心思最多的一部分。

模型服务商的 prompt cache 依赖请求前缀保持不变。多轮对话里，客户端每次都会把完整历史重新发一遍。如果插件只在最新一轮注入参考文本，那么到了下一轮，上一轮的用户消息里就没有这段文本了，前缀发生变化，缓存失效。如果每一轮都重新查询，又可能因为记忆库更新而得到不同的结果，前缀同样会变。

插件的做法是在进程内为每个会话维护一个缓存，记录每一轮用户消息当时注入的参考文本。处理新请求时，先把历史里每一轮用户消息当初注入的那段原样补回去，再只为最新一轮做新的查询。这样历史部分逐字节保持一致，缓存可以继续命中。

同一轮用户消息还可能被发送多次。Agent 调用工具、拿到结果后继续推理，客户端会带着同一条用户消息再发一次请求。插件识别到是同一轮之后，会直接复用缓存里的参考文本，不再查询服务。

这个缓存有明确的上限：所有会话合计 8 MiB，最多 256 个会话，每个会话最多 128 轮，超出时按最久未使用的顺序整个会话淘汰。缓存的键包含来源分类和协议，不同来源的请求互相隔离，即便开启了远程召回也一样。需要说明的是，这个上限约束的是缓存内容的大小，不是 Bun 进程的总内存。被淘汰的轮次之后会重新查询，所以在内存压力下前缀保持只能做到尽力而为。

### 失败时放行

召回链路上任何一步出问题，包括超时、服务不可用、鉴权失败、返回格式不认识、找不到 Scope，插件都会放弃这次注入，让请求原样发给模型。客户端取消请求时，正在进行的服务请求会一并中止，而且取消不会触发退避。

对用户来说，记忆服务的状态不会影响模型能否正常回答，最坏的情况是这一轮没有召回内容。

## 六、存回链路的实现细节

### 什么时候写

存回发生在 `onResponse` 里，也就是回复结束之后。失败、被截断或不完整的回复不会存。

一个多轮会话如果每一轮都写一次，服务端会收到大量重复的前缀内容。插件对每个会话做了一个简单的合并：回复结束后先把对话暂存起来，启动一个空闲计时器，默认十分钟。如果十分钟内同一会话又来了新的一轮，并且历史是在之前的基础上继续，那么用新的完整对话替换掉暂存的那份，重新计时；如果历史和暂存的不一致，比如用户回退编辑了之前的消息，就先把暂存的那份写出去。计时器到期后，暂存的对话才真正写入。

写入接口是 `v1/sources/content`，元数据里标注来源为 `magpie`、事件为 `conversation_completed`，同时带上协议类型。会话 ID 和工作目录在元数据里同样只保留 SHA-256 摘要。写入有单独的十秒超时，失败不自动重试。

### Responses 协议的历史还原

OpenAI Responses 协议允许客户端通过 `previous_response_id` 引用服务端保存的上一轮，而不是每次都把完整历史发过来。这种情况下插件看到的请求里只有增量内容，直接存下来会是一段残缺的对话。

插件的处理方式是记录自己经手过的每个响应的完整输入和输出，遇到 `previous_response_id` 时据此拼出完整历史，只用于存回，不改动发给模型的请求。如果引用的历史不是这个进程经手的，比如 Magpie 重启过，插件就放弃这次存回，而不是存一份不完整的对话假装它是全部。

### 凭证检查

存回的内容包括工具调用的参数和结果，Agent 读过的文件、执行过的命令输出都在里面，难免会出现密钥。插件在暂存之前会检查用户消息文本和工具参数、结果，覆盖的情况包括常见的凭证赋值写法、JSON 字段、带前缀的环境变量（包括 `PGPASSWORD`、`MYSQL_PWD`）、URL 里的 `user:password@`、Stripe 的 `sk_live_` 和 `rk_live_` 密钥、Google 的 `AIza` 密钥等。检查是在 JSON 序列化之前、针对结构化的参数做的，避免转义后漏判。

命中后整段对话都不存，而不是只把命中的部分打码。打码很难做干净，残留的上下文本身就可能泄露信息。

这个检查只是一道保险，不能识别任意格式的秘密，比如散文里写的密码或者命令行里的密码参数。所以存回保持默认关闭，开启前需要用户确认这些对话可以存到自己配置的服务里。

### 存回的内容会去哪里

存回的对话会被 PowerContext 的 Memory 和 Topic Memory 调度处理。需要特别说明的是，它们不会进入 Experience。PowerContext 的 Experience 只处理元数据里标注为任务结果的来源，这类来源需要 Agent 在任务真正完成或中断时，通过 PowerContext MCP 的 `record_task_outcome` 工具主动记录。

插件不会从对话里推断任务结果，因为助手回复里声称“已完成”并不等于任务真的成功，把它当作事实记录下来会污染经验库。需要 Experience 的话，可以在客户端单独接入 PowerContext 的 MCP Server，和本插件同时使用互不冲突。同理，需要 Agent 主动搜索或写入记忆时，也是通过 MCP 来做，插件本身不提供任何工具。

## 七、review 过程

这个插件的 PR 是 [magpie-community/plugins#117](https://github.com/magpie-community/plugins/pull/117)，10 月 14 日提交，10 月 29 日合并，中间经历了多轮 review。合并时新增约 2900 行，其中测试约 1100 行，配置页约 650 行，插件代码约 800 行，其余是文档。现在回头看，插件的很多设计都是在 review 中逐步形成的，这里简单记录几个关键的转折。

**去掉自动安装。** 最早的版本想做到开箱即用：插件安装时自动下载 uv 的安装脚本，装好 Python 和 PowerContext，再由插件负责启动和看护服务进程。维护者 review 时首先指出，运行时下载并执行 shell 脚本、从 PyPI 安装包，对一个社区插件来说风险太大，而且服务的生命周期不应该由网关插件来管理。后来我把这部分全部删掉了，插件只负责连接一个已经部署好的服务。这样插件变成了几个纯 `.mjs` 文件，没有依赖，没有可执行入口，也不需要 lockfile，审查起来简单得多。

**存回改为默认关闭。** 第二轮的意见集中在存回上：不能有默认的服务地址，存回必须默认关闭，开启后也只能处理本机请求。

**召回也要限制来源。** 修完存回之后，维护者又发现了一个我漏掉的边界：上一版只限制了存回的来源，召回没有限制。也就是说，通过共享密钥接入的其他人仍然可以把查询发到我的服务，并拿到我的记忆。修正后，召回在解析 Scope、访问缓存或发出任何请求之前就先检查来源，存回权限和召回权限彻底分开。

**凭证检查和测试时序。** 后面几轮主要是加强凭证检查的覆盖范围，以及修正测试里的时序问题。一开始我给所有测试请求都设了 50 毫秒的超时，在维护者机器负载较高时会因为传输延迟而失败。后来改成正常请求保持 1000 毫秒的超时，只对故意挂起的请求在服务端收到之后再缩短超时，退避逻辑则通过替换 `Date.now()` 来推进时间，不再依赖真实的等待。

**跟随宿主正式版本调整入口。** 异步 hook 正式发布时入口名改成了 `magpie.hooks`，插件也随之把入口文件改名为 `powercontext.hooks.mjs`，并更新了清单和检查脚本。

现在插件仓库里有六十多个测试用例，用模拟的 HTTP 服务覆盖了召回、存回、超时、退避、来源限制、凭证检查和缓存行为，不需要真的启动 PowerContext。连接真实服务的端到端验证在我本地单独跑，结果贴在 PR 里。

## 八、配置页

插件还带了一个配置页，只使用了 Magpie 已经发布的 `magpie.options.get/set` 和主题桥接接口，没有为此新增任何宿主 API。

页面上可以查看当前的连接摘要，打开连接配置对话框填写地址、Scope ID 和密钥，切换存回开关，并说明召回和存回分别会向服务发送哪些内容。保存时会保留用户在 JSON 编辑器里配置的其他高级选项。页面跟随 Magpie 的浅色、深色和跟随系统三种主题，深色模式下使用 PowerContext 官方的反色图标；语言跟随 Magpie 的设置，支持简体中文、繁体中文、英语、日语和德语，切换语言时不会丢失尚未保存的表单内容。

有一点需要说明：密钥保存在 Magpie 本地的插件配置里，不在系统钥匙串中。如果之前用环境变量 `POWERCONTEXT_AUTHORIZATION` 配置过凭证，在页面上没有填写密钥时仍然会读取这个变量。

## 九、已知的限制

最后把目前的限制集中列一下，方便大家评估是否适合自己的场景：

- 存回是尽力而为的。Magpie 进程退出时，暂存中尚未写入的对话会丢失；写入失败不重试，一个会话分多段写入时，中途失败后剩余部分也不再写。
- 召回缓存在进程内，Magpie 重启后会重新查询，第一次请求的前缀和之前可能不同。
- 凭证检查无法覆盖所有格式的敏感信息。
- 插件不负责 PowerContext 的部署和运维，记忆提炼的质量取决于服务端配置的生成模型。
- 存回的对话不会进入 Experience。

## 写在最后

这个插件从提 issue 到合并用了两周多。比起写代码本身，更多的时间花在了想清楚边界上：网关能做什么、不该做什么；哪些数据默认可以发、哪些必须用户明确同意；服务出问题时怎样才不影响正常使用。这些问题在 review 中被一次次追问，最后的结果比我最初的设计克制得多，也更值得信任。

感谢 Magpie 的维护者 yetone 在 review 中逐行阅读代码、亲自运行验证，并把异步 hook 移植进主线。也欢迎大家试用插件，遇到问题可以到插件仓库提 issue，或者到 Magpie 的 [Discord](https://discord.gg/vGSnD3ZKQF) 交流。如果你有其他想在网关层做的事情，现在也可以基于 `magpie.hooks` 来写了。
